Charte de codage ACE3i
Cette page wiki décrit la charte de codage et de configuration technique sur les projets ACE3i.
La charte de codage concerne le process allant de la création du projet jusqu'à son passage sur
SonarQube.
Le codage d'un projet commence soit par la création de ce projet dans l'IDE (s'il s'agit d'un
nouveau projet) ou soit le clonage de ce projet depuis le dépôt gitlab (s'il s'agit d'un projet
déjà existant) ;
Nous utilisons maven pour le build du projet. De ce fait, lors de la création du projet, il faut
indiquer le groupId et le artifactId. le groupId doit être sous la forme com.ace3i.xxxxx et
l'artifactId sous la forme ace3i-yyyyy. xxxxx est le namespace correspondant à la catégorie
de projets ace3i à laquelle appartient ce projet. yyyyy est le nom du projet actuel. Exemple
de groupeId: com.ace3I.epaiement, artifactId: ace3i-epaiement-online-core
Une fois le projet créé, il faut utiliser les librairies de base dans le projet en important ces
librairies dans le pom du projet en plus des dépendances spécifiques ;
Dans le projet, les packages sont organisés en couches: la couche DAO (comportant les
classes d'accès à la base de données), la couche métier (comportant les classes services ou
classes de traitement métier) et la couche web (comportant les classes qui exposent des api
REST). Les différents packages standards qui se retrouvent dans les projets sont les suivants:

1. com.ace3i.xxxxx.yyyy.entity: package des classes entités ;
2. com.ace3i.xxxxx.yyyy.repository: package des classes repository ou classes DAO ;
3. com.ace3i.xxxxx.yyyy.repository/spec: package des classes de spécifications spring (classes
utilisées dans les recherches multicritères) ;
4. com.ace3i.xxxxx.yyyy.service: package des classes services ou classes métier ;
5. com.ace3i.xxxxx.yyyy.service/impl: package des implémentation des services déclarés dans
le package service ;
6. com.ace3i.xxxxx.yyyy.controller: package des classes RestController qui exposent les api
REST ;
7. com.ace3i.xxxxx.yyyy.exception: package des classes d'exceptions ;
8. com.ace3i.xxxxx.yyyy.util: package des classes utilitaires.
Dans le cas où le nom du projet se retrouve dans le groupeId, il faut garder un des deux.
A cela peuvent, éventuellement, s'ajouter d'autres packages ci-dessous selon le besoin :

1. com.ace3i.xxxxx.yyyy.config: package des classes de configuration. Par exemple les classes
de configuration pour un accès multi bases de données ou bien les classes de configuration
dans le cas d'une architecture micro service ;
2. com.ace3i.xxxxx.yyyy.client: package des classes client qui consomment des api SOAP ;
3. com.ace3i.xxxxx.yyyy.annotation: package des annotations personnalisées ;
4. com.ace3i.xxxxx.yyyy.aspect: package de configuration des aspects ;
5. com.ace3i.xxxxx.yyyy.cron: package des tâches planifiées et automatisées ;
6. com.ace3i.xxxxx.yyyy.dto: package des classes DTO ;
7. com.ace3i.xxxxx.yyyy.filterform ou com.ace3i.xxxxx.yyyy.finder: package des classes à
utiliser sur les formulaires de recherche multicritères ;
8. com.ace3i.xxxxx.yyyy.mapper: package classes des mapper personnalisés ;
9. com.ace3i.xxxxx.yyyy.listener: package des classes des listeners personnalisés;
10. com.ace3i.xxxxx.yyyy.model: package des classes pojo utilisés dans la communication avec
les autres service (Ex: lors des accès aux api externes) ;
11. com.ace3i.xxxxx.yyyy.report: package des classes utilisées pour l'édition des états.


Les noms des tables correspondant aux classes entités suivent une convention ACE3i. Le
nom est constitué de 5 caractères: les deux premiers caractères concernent le nom du
projet ou de module et les 3 derniers correspondent au nom de l'entité. Par exemple pour
l'entité Client dans le projet epaiement online, le nom de la table peut être EPCLI où EP
correspond à EP dans EPaiement et CLI correspond à CLI dans CLIent ;
Au niveau des noms des champs des tables, les 3 premiers caractères correspondent au 3
derniers caractères dans le nom de la table et le reste du nom du champ (3 à 4 caractères
maximum) correspond à l'attribut associé. Par exemple, pour l'entité Client, le champ associé
à l'attribut codeClient aura pour nom: CLICOD ;
Les noms des repository doivent être sous la forme xxxxRepository où xxxx est le nom de
l'entité. Ex: ClientRepository ;
Les noms des spécifications doivent être sous la forme xxxxSpec où xxxx est le nom de
l'entité. Ex: ClientSpec ;
Les noms des services doivent être sous la forme IxxxxService où xxxx est le nom de l'entité.
Ex: IClientService ;
Les noms des implémentations des services doivent être sous la forme xxxxService où xxxx
est le nom de l'entité. Ex: ClientService ;
Les noms des controller doivent être sous la forme xxxxController où xxxx est le nom de
l'entité. Ex: ClientController.
